# Окна применения запускает внешний таймер Cloudflare

11 октября 2026 года пользователь выбрал основной таймер окон применения: Cloudflare Workers Cron Trigger на бесплатном плане отправляет пустой `workflow_dispatch` в private repo установки. Нативный `on: schedule` остаётся только редким статическим резервом. Основание — исследование `outputs/auto-reset/research/cron-delivery-research.md` и три когорты 9–10 октября (`outputs/auto-reset/research/delivery-2026-10-09`, `delivery-2026-10-09-r2`, `delivery-2026-10-10-r3`, диагностика `diagnosis-2026-10-10`): 39 датированных слотов, 0 schedule runs. GitHub не обещает доставку `schedule` ни по задержке, ни по доле ([документация](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)). Свежие регистрации расписания уязвимы: сотрудники GitHub подтвердили такой сбой в январе 2026 ([#185024](https://github.com/orgs/community/discussions/185024)), а с августа 2026 сообщество сообщает о задержках 2–10 часов и пропусках. Окно при Δ = 1 час такую задержку не переживает, а программа переписывает cron перед каждым окном. GitHub-only альтернативы не укладываются в лимит 1 000 минут с резервом 100 или не защищают от потери события: долгоживущая job, частый постоянный cron и self-rescheduling (раздел 5 исследования).

Worker тикает раз в 5 минут (`2-57/5 * * * *`), определяет, попадает ли текущая UTC-минута в опубликованные окна, и только тогда отправляет один пустой dispatch без inputs. Источник правды об окнах — тот же скомпилированный план `schedule-planner`; где он хранится для Worker, решает 37. Worker не решает, применять ли сброс: повтор, `nextAttemptAt`, граница, запрет раннего consume, stop-on-unknown, disable/version и concurrency остаются в state и workflow, поэтому поздний или двойной тик даёт обычный безвредный reconcile. Ошибка чтения или непонятный план — fail-closed без dispatch. Нативный резерв — статический cron раз в сутки на минуте вне начала часа: он выполняет reconcile и сообщает в Summary, если внешнего тика давно не было. Резервный cron не переписывается перед окнами, поэтому окна больше не зависят от свежей регистрации.

Таймер получает отдельный **токен таймера** — fine-grained PAT только на один repo, Actions: write + Contents: read, со сроком действия и ротацией; хранится как Worker secret. Основной PAT установщика, Repository Secrets, сессия ChatGPT и state в Cloudflare не попадают. Обязательное условие включения — внешний тик не может передать команду: Actions: write позволяет dispatch с непустым input, поэтому открытый `command` закрывается в 34 до первого живого Worker. Включение в production также требует успешного E1 (35); если критерий E1 не выполнен, решение возвращается на пересмотр, а 36 не начинается.

**Пересмотр решения 04** («GitHub Actions выбран»; Cloudflare в ответе 04 перечислен среди не входящих в реализацию). Противоречие: в установке появляется сервис вне GitHub. Причина: внутри GitHub на private Free нет надёжного отложенного триггера, а `workflow_dispatch` в тот же период стартовал за секунды. Сохраняется: исполнитель — GitHub-hosted runner в private repo пользователя; account RPC, credentials и state живут только там; продукт бесплатен, своего сервера нет, runtime и таймер не вызывают модель. Cloudflare — таймер, а не исполнитель.

**Пересмотр решения 12** («один PAT для установки и работы»). Противоречие: появляется второй GitHub-токен с другим жизненным циклом — со сроком и ротацией, тогда как основной PAT после setup не отзывается. Причина: основной PAT нельзя отдавать третьей стороне, а таймеру нужен только запуск и чтение плана. Сохраняется: основной PAT остаётся единственным токеном установки и работы с прежними правами (их возможное сужение — 37/38), discovery раз в 4 часа, лимит 1 000/резерв 100, Δ по умолчанию час. Отдельный Plan:read токен из уточнения 9 октября остаётся. ADR-0001 не затрагивается.

**Последствия.** Пользователю нужен аккаунт Cloudflare; сторонний сервис хранит токен таймера; его утечка позволяет запускать или отключать workflow и читать репозиторий (state без credentials), но после 34 не позволяет передавать команды. Cloudflare тоже не обещает пунктуальность, а изменения триггеров распространяются до 15 минут ([Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)). 288 вызовов в сутки намного ниже лимитов Free ([limits](https://developers.cloudflare.com/workers/platform/limits/)). Оценка расхода Actions: discovery 360 + окна 2–96 + резерв 60 + запас 100 = 522–616 минут в месяц. Остановку таймера замечает только резерв, а не пользователь в момент окна. Если пользователь откажется от стороннего сервиса, честный вариант — managed cron со статусом best effort.

**Отвергнуто.** Долгоживущая job защищает только от задержки меньше оплаченного запаса и не защищает от потери стартового события; при L ≥ 2 ч превышает бюджет. Постоянный частый cron стоит 1 440–17 280 минут. Self-rescheduling без отложенного dispatch оплачивает ожидание (43 200 минут в месяц) и рвётся при любом сбое. cron-job.org без своей логики дёргает всегда (8 640 dispatch в месяц), а хранение заголовков с токеном не описано. Публичный репозиторий-таймер раскрывает моменты сбросов, хранит PAT к private repo в public и попадает под ограничения Additional Product Terms для Actions.

**Уточнение 14 октября (тикеты 37–38).** Права основного PAT не сужены: `Workflows: write` нужен только bootstrap и явному Upgrade, повседневная работа пишет план таймера через Contents. Установщик принимает токен таймера скрыто, проверяет его чтением repo и плана, передаёт в Worker secret через Wrangler и сохраняет в state только срок действия. Enable запрещён, пока пустой dispatch Worker в пробный слот не подтверждён; до допуска пилота такой dispatch выполняет только reconcile, как резервный запуск.

**Пересмотр 14 октября 2026.** Раздел о токене таймера заменён [ADR-0003](0003-single-token-timer-app.md): таймер получает GitHub App с ключом в Worker secret, отдельного PAT со сроком нет; billing читается токеном установки.

**Заменено** [ADR-0004](0004-github-only-worker.md) 19 октября 2026.
