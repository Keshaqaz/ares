# Один токен установки, таймер — через GitHub App

14 октября 2026 года пользователь выбрал схему, в которой он выпускает и копирует ровно один токен. **Токен установки** — fine-grained PAT только на private repo установки: Contents, Secrets, Actions, Variables, Workflows — write и Account permissions → Plan: read; форма просит срок 366 дней, но фактический срок может оказаться короче (тикет 39). Он заменяет и основной PAT, и отдельный billing-токен. Внешний таймер вместо второго PAT получает **приложение таймера**: GitHub App пользователя с правами только Actions: write и Contents: read, с выключенным webhook, которое пользователь устанавливает на repo установки. Его private key (**ключ таймера**) хранится только как Worker secret; Worker перед dispatch сам выпускает installation token на час.

**Токен установки.** Установщик открывает предзаполненную форму `https://github.com/settings/personal-access-tokens/new` с именем, описанием, `expires_in=366` и правами ([документация](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)); repo пользователь выбирает сам — URL его не задаёт. Токен хранится в Repository Secret `AUTO_RESET_GITHUB_TOKEN` и локально в macOS Keychain, поэтому повторный запуск установщика его не спрашивает. Срок читается из `GitHub-Authentication-Token-Expiration` и хранится в state; за 14 дней до истечения напоминают установщик, `s` и Actions Summary. Ротация — существующий `rotate-grant`, после результата обновляется Keychain. Billing provider читает usage тем же токеном; Secret `AUTO_RESET_BILLING_TOKEN` удаляется миграцией.

**Приложение таймера.** Установщик регистрирует App через [manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest): локальная страница на loopback отправляет manifest с `default_permissions` `actions: write`, `contents: read` и `hook_attributes` с URL-заглушкой и `active: false`; пользователь нажимает Create, установщик обменивает code на private key в течение часа, затем пользователь устанавливает App на repo установки. Установщик переводит ключ в PKCS#8 и передаёт Wrangler через stdin; в state попадают только App ID и installation ID. Worker подписывает JWT (RS256, WebCrypto) и запрашивает installation token, ограниченный repo и теми же двумя правами; права токена не могут превышать права App. Подтверждение пробным пустым dispatch, запрет enable без него и запрет открытых команд (34) сохраняются.

**Пересмотр ADR-0002, раздел «Токен таймера».** Противоречие: у таймера больше нет fine-grained PAT со сроком и ротацией. Причина: пользователь копирует один токен вместо трёх, у таймера исчезают срок, напоминание и ротация (тикет 38: пауза → `c` → проба → enable). Сохраняется: Cloudflare — таймер, а не исполнитель; в Cloudflare нет токена установки, Repository Secrets, сессии ChatGPT и state; утечка ключа позволяет только запускать/отключать workflow и читать repo, но не передавать команды.

**Пересмотр решения 12 и уточнения 9 октября.** Отдельный Plan:read токен упраздняется: он хранился в тех же Repository Secrets и читался теми же jobs, поэтому изоляции не давал. Решение 12 («один PAT для установки и работы») восстанавливается в полном смысле. ADR-0001 не затрагивается.

**Последствия.** У ключа таймера нет срока: защиту сроком заменяет отзыв ключа или удаление App в GitHub. GitHub не выпускает ключи App через API, поэтому замена ключа — ручная генерация на странице App. У пользователя появляется App в Settings → Developer settings; uninstall просит удалить его. Токен установки по-прежнему нельзя выпустить через API: раз в год пользователь нажимает Generate в предзаполненной форме. Сочетание Plan: read с правами repo в одном токене, loopback `redirect_url`, предвыбор repo при установке App и ключи прав в URL проверены тикетом 39 — см. пересмотр ниже.

**Отвергнуто.** Отдать Cloudflare токен установки: утечка у третьей стороны давала бы запись в Secrets и ключ admin-команд. Всё на GitHub App без PAT: billing usage GitHub разрешает App только через user access token ([permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps)), это 8-часовой токен с одноразовым refresh на полгода — ещё один протокол надёжной ротации ради одного Generate в год; Worker всё равно требовал бы отдельный узкий App. Workflow, передающий Worker короткие токены: `GITHUB_TOKEN` гаснет с job, а запись в Worker требует ещё одного credential.

**Пересмотр 16 октября 2026 (тикет 39, живые проверки владельцем).** Подтверждены: один PAT с правами repo и Plan: read читает billing тем же контрактом; loopback `redirect_url`; installation ID через JWT; узкий installation token; dispatch отвечает 200 с `workflow_run_id`; RS256 через WebCrypto в `workerd`. Не подтвердились три допущения, решения пользователя:
- **Срок.** Предзаполненная форма с `expires_in=366` дала токен на 30 дней. Установщик принимает любой срок: читает его из `GitHub-Authentication-Token-Expiration`, а если он меньше 366 дней, показывает дату и подсказывает перевыпуск на год. Напоминание за 14 дней считается от фактического срока.
- **Один repo.** Ни форма PAT, ни ссылка установки App (`repository_ids[]`) repo не ограничивают: по умолчанию получилось «All repositories». Установщик проверяет оба — токен по списку видимых private repo, App по `repository_selection` — и при доступе шире repo установки **предупреждает и продолжает**, подсказывая «Only select repositories». Плата за это решение: широкий токен установки в Repository Secrets даёт запись во все repo владельца; утечка ключа таймера при установке на все repo позволяет запускать и отключать workflow и читать содержимое всех repo, а не только repo установки. Worker по-прежнему сужает каждый installation token до repo установки и двух прав.
- **Webhook.** Manifest без `hook_attributes.url` отклоняется; используется URL-заглушка с `active: false`.
