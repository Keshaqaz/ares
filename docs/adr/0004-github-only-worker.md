# Воркер на статическом расписании GitHub Actions, без Cloudflare и App Server

19 октября 2026 года пользователь сменил приоритет: максимальная простота установки важнее пунктуальности. Опоздание применения на 1–2 часа допустимо, если сброс не теряется в последний день срока. Установка сводится к `brew install`, входу в GitHub и входу в ChatGPT. Скрипт сам создаёт приватный репозиторий воркера в аккаунте пользователя.

**Решение.**
- Воркер — единственный workflow со **статическим** `schedule`, который после установки не переписывается. На каждом тике он сам решает, применять ли сброс. Частота выбирается по замеру задержки (ветка `prototype/cron-lag`) и бюджету 2000 минут Free.
- Ядро — прямые HTTP-запросы: `GET /wham/usage`, `GET /wham/rate-limit-reset-credits`, `POST /wham/rate-limit-reset-credits/consume` к `chatgpt.com/backend-api` и refresh через `auth.openai.com/oauth/token` с `client_id` Codex. App Server, runtime pins, bubblewrap и Node pins не нужны.
- Вход в ChatGPT — device-code поток по HTTP. Это отдельная сессия воркера, а не копия `~/.codex/auth.json`, потому что refresh token ротируется и повторное использование отклоняется (`refresh_token_reused`; короткое окно, в котором повтор ещё принимают, — см. «Проверка 19 октября 2026»).
- Сессия и state лежат в репозитории воркера зашифрованным файлом, который воркер коммитит сам через `GITHUB_TOKEN` с `contents: write`. Ключ шифрования — Actions secret, его один раз задаёт установщик.
- Новую сессию после её потери (`login`) CLI передаёт воркеру через одноразовый Actions secret `WORKER_LOGIN`: открыть зашифрованный state CLI не может, а без шифрования сессии в репозитории не место. Воркер берёт её один раз и только для прежнего аккаунта ChatGPT, вердикт публикует в открытой сводке, а CLI удаляет секрет сразу после run. Это не «Actions secret для сессии» из «Отвергнуто»: постоянной сессией воркера остаётся state, и писать секреты воркеру не нужно.
- GitHub — своё OAuth App с device flow (scope `repo`, `workflow`). Токен хранится только в macOS Keychain и используется CLI для установки, статуса, «Применить сейчас» и изменения правил. Управление идёт только через CLI.
- Код воркера установщик кладёт в репозиторий пользователя собранным файлом и не подключает как внешний action.

**Заменяет** ADR-0001 (App Server получает только access token), ADR-0002 (внешний таймер Cloudflare) и ADR-0003 (токен установки и приложение таймера). Противоречие с ADR-0002 — опора на `schedule`, который тогда дал 0 из 39 доставок. Причина пересмотра: те когорты переписывали cron перед каждым окном (каждый раз свежая регистрация) и удаляли файл через 40–70 минут, то есть не отличали задержку в часы от потери. Статический cron и допуск в часы — другой режим, и его проверяет замер. Если замер покажет пропуски, которые не укладываются в окно перед истечением, решение возвращается на пересмотр.

**Последствия.**
- У пользователя нет аккаунта Cloudflare, PAT, GitHub App и ежегодного перевыпуска токена.
- OAuth-токен GitHub в Keychain имеет доступ ко всем репозиториям пользователя (цена простоты, как у `gh`).
- Сбой между refresh и коммитом теряет сессию: пользователь получает письмо о failed run и входит заново. Окно риска сужают refresh только перед истечением access token и один run за раз.
- Неизвестный результат consume больше не останавливает цикл (прежний stop-on-unknown): `redeem_request_id` фиксируется в state до POST, повтор идёт с тем же ключом, успех сверяется со списком сбросов.
- Не проверены до первого живого запуска: consume с честным `User-Agent` и идемпотентность consume по `redeem_request_id`. Чтение квот и сбросов с любым `User-Agent`, device-вход и refresh проверены 19 октября (ниже).

**Отвергнуто.** Cloudflare и любой внешний таймер — лишний аккаунт. Свой сервер — пользователь его не хочет. Локальный запуск — компьютер бывает выключен. Публичный репозиторий — раскрывает расписание и шифротекст сессии. Reusable action из нашего репозитория — цепочка поставки к сессиям всех пользователей. Actions secret для сессии — требует долгоживущего токена GitHub внутри воркера.

**Проверка 19 октября 2026 (тикет 01, живой прогон на аккаунте разработчика).** Одноразовый скрипт без Codex прошёл device-вход, чтение квот и сбросов, refresh и повторное чтение. Все запросы шли с `User-Agent: codex-auto-resets/0.1.0` без `originator`, и ни один не получил отказ, поэтому Codex-совместимые заголовки не нужны.
- Device-вход по HTTP работает без изменения настроек безопасности ChatGPT. В `id_token` есть claim `chatgpt_account_id`.
- Refresh выдаёт новый refresh token, то есть ротирует его. Access token живёт 10 суток (`exp − iat` = 864000 с) и после входа, и после refresh, так что refresh только перед истечением access token нужен примерно раз в 10 дней.
- Старый refresh token через несколько секунд после ротации приняли повторно (200, без `refresh_token_reused`). Значит, у сервера есть окно, в котором повтор допускается, но его длина не измерялась. От двойного refresh защищает только правило «один run за раз», а не отказ сервера.
- После `POST /oauth/revoke` с последним refresh token (200) следующий refresh получил 401 `refresh_token_invalidated`. Revoke шёл сразу после повторного использования старого токена, поэтому прогон не различает, что аннулировало сессию: revoke или обнаружение повтора. Токены, выданные на повторный refresh, скрипт не читал и не отзывал. Срок жизни refresh token неизвестен, и если их не аннулировало вместе с семейством, они остаются действительными. Токены нигде не сохранялись и не печатались.
