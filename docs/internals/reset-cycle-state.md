# Состояние циклов и команды (тикет 14)

Реализовано 8 октября 2026 года. Все времена — Unix-секунды. Метаданные и семантика ответа consume принадлежат `AccountAdapter` из 13; новые модули отвечают за сохранение выбора, границы и историю запросов/команд. Credentials не входят в state. Локальный JSONL CLI предоставляет synthetic modes; private Actions job и host bridge описаны в `docs/internals/private-workflow.md`, живое включение требует gate владельца `AUTO_RESET_PILOT_APPROVED` (проверено в пилоте 21).

## Модули и границы

- `src/core/state-store.mjs`: `FileStateStore`, явная инициализация, проверка схемы/связей, миграция, версия записи, сериализация writer.

- `src/core/cycle-report.mjs`: Markdown-отчёт ru/en, пригодный для будущего Job Summary.
- `test/reset-cycles.test.mjs`: общий набор проверок состояния для переиспользования в 17; `test/support/cycle-crash-fixture.mjs` завершает отдельный процесс в трёх точках отказа.

Хранилище здесь — **локальный файл**, а не реализация GitHub storage. Передача authoritative state между временными runners, публикация auth — storage 15 и host lifecycle 23, долговечная очередь/dispatch — 17. Planner/quota/horizon/cron — 16. Отдельные внешние уведомления не добавлены: решение 12 оставляет Actions/Job Summary.

Контракт хранилища для следующих тикетов:

- `read()` возвращает текущую проверенную запись, не checkout/event snapshot.
- `update(fn)` выполняет синхронную мутацию под эксклюзивным writer; изменённый state сохраняется до возврата. Версия увеличивается только при изменении. Ошибка записи останавливает выполнение вызывающего кода.
- `inspect(fn)` читает текущую запись под той же сериализацией. Финальная проверка и синхронный вызов отправки RPC происходят внутри callback; ожидание ответа — после освобождения writer.
- Все account-операции установки должны проходить через один engine/адаптер. Нельзя параллельно выполнять raw consume вне журнала. Host OAuth/publication из 23 завершаются до external login; final consume проверка в 17 выполняется после обслуживания/startup. Протокол storage из 15 сохраняется; live mode ждёт 23/17/21.

## State и запись

Схема 1 хранит `version`, язык/default Δ, сохраняемые общие правила `weeklyAutoReset` и `beforeExpiry` (обе по умолчанию `false`; миграция не включает автоматизацию без выбора владельца), необязательный `weeklyWatchUntil` (окно наблюдения при 99% недельной квоты), disable/revoke/reconnect, выбранные и исторические циклы, минутные группы, журнал запросов и принятых command ID. Цикл включает выбранный ID, источник `trigger` (`expiry` — правило срока, `weekly` — недельное правило, `manual` — «применить сейчас»/retry; отсутствие — явный `select`), expiry, все связанные ключи групп, `scheduledAt`, `originalDeadline`, актуальную `deadline`, признак часового цикла/наличия расписания, `nextAttemptAt`, последнюю попытку/результат и проблему metadata.

Файл записывается через новый временный файл с правами 0600: write → fsync файла → rename → fsync каталога. Неудачная запись intent запрещает RPC; неудачная запись результата сохраняет неизвестность старого intent. Семантика физической устойчивости зависит от файловой системы; это не доказательство GitHub persistence или поведения при отказе всего диска.

Миграция 0 → 1 принимает только тот же проверяемый layout без `commands`, добавляет пустой журнал команд и сохраняет всю историю consume/групп. Это предусмотренный тестовый предшественник первой схемы, а не поддержка произвольных старых файлов. Известная миграция записывается при следующем изменении. Другая версия/повреждение останавливают consume. Отсутствующий файл не инициализируется автоматически: сначала восстановить историю установки; `init` предназначен для новой установки.

Локальный writer использует эксклюзивный каталог `<state>.lock` с PID/hostname. Конкурентный writer получает `state_busy`. Crash внутри короткой файловой критической секции может оставить lock. `recoverInterruptedWriter({expectedPid, serialized: true})` разрешён только единственному сериализованному оператору; проверяет hostname и отсутствие процесса через PID. Живой, чужой или ownerless lock не снимается; PID reuse оставляет безопасную блокировку. Метод удаляет только lock, не state/журнал. Автоматического снятия по времени нет. Private CI реализует свой writer поверх authoritative storage в 17.

## Циклы и восстановление

- Минутный ключ — `minute:${floor(expiresAt / 60)}`. Дата входит в ключ; timezone интерфейса не участвует. Явный `select` без ID выбирает самый ранний допустимый точный срок только из полного списка. Partial/countOnly/unavailable требуют явного допустимого ID и не меняют выбор при отказе. После выбора нет автоматической подстановки другого ID.
- Конечный цикл: начало `expiry − Δ`, исходная граница expiry, без часового сокращения. Неизвестный/бессрочный срок с выбранной датой: граница `выбранное начало + 3600`, в том числе для опоздавшего первого run.
- `automation: false` означает отсутствие расписания: отчёт показывает null для целевого момента/границы. Позднейшее `apply-now` начинает выбранный цикл.
- Уточнение expiry сохраняет начало/исходную границу, уменьшает актуальную границу и связывает новые группы со всеми старыми циклами/запросами ID. Ошибка/refresh/reconnect/resume не продлевают цикл. Ранее известный срок не стирается при неполном чтении или более позднем сроке.
- Если ранее отдельно выбранные ID окажутся в одной минуте, дополнительные consume останавливаются. Явный `select` может разрешить конфликт только при отсутствии успеха и неизвестного consume.
- До отправки сохраняются request ID, выбранный ID, ключ идемпотентности, группы, `unconfirmed`, время и `nextAttemptAt = время + 300`. До резервирования проверяются начало, прошлый next attempt и исключительная граница. Повторный queued run не наверстывает пропущенные слоты.
- Общие правила (терминальный интерфейс, решение пользователя 14 октября 2026). Правила создают циклы только из полного списка (`details`/`empty`), по одному ID на минутную группу, не поверх успеха, неизвестного исхода или живого цикла другого ID; явный выбор и ручной цикл имеют приоритет. Выключенное правило не публикует окон своих циклов и не отправляет по ним consume (`rule_disabled`).
  - `beforeExpiry`: для каждого допустимого сброса окно `expiresAt − 1800` … `expiresAt`; consume **без** недельного условия.
  - `weeklyAutoReset`: при свежем подтверждённом исчерпании недельной квоты сразу создаётся цикл для сброса с ближайшим сроком: начало — момент чтения, граница — `min(expiresAt, недельный resetsAt)`. Чтение, показывающее 99% (но не 100%) недельного окна, задаёт `weeklyWatchUntil = min(сейчас + 3600, resetsAt)`: планировщик публикует это окно, внешний таймер будит чтения раз в 5 минут. Процент — только сигнал наблюдения, не разрешение consume.
  - «Применить сейчас» (`apply-now`) и `retry` создают цикл `manual`: consume **без** недельного условия и без галочек. `apply-now` без предварительного `select` берёт строку из последнего сохранённого списка `installation.metadata` (чтение внутри команды изменило бы версию обслуживанием авторизации); без списка читает metadata как `select`. Пригодность строки повторно доказывает свежее чтение перед consume. Закончившийся без успеха цикл правила или ручной цикл не удерживает сброс: `apply-now` начинает новый.
- Явный `select` и недельное правило сохраняют недельный guard: включённая `weeklyAutoReset` и подтверждённое исчерпание **недельной** квоты: identity-bound `ordinaryUsageAllowed=false`, обычный `rate_limit_reached` без spend restriction и окно `windowDurationMins=10080` с `usedPercent=100` и будущим `resetsAt`. Окна различаются по подтверждённой длительности, а не по позиции primary/secondary; evidence действительно до `min(resetsAt, начало чтения + 300с)`. Guard проверяется до резервирования и повторно под writer непосредственно перед send; устаревшее/противоречивое/неизвестное недельное состояние или только пятичасовое исчерпание дают `notSent` без consume. Проверка чтения при исчерпании (observer 21) — отдельный evidence, не условие применения.
- Под актуальным writer непосредственно перед RPC снова проверяются версия, disable/revoke, группы и `now < deadline`. Next attempt относится к **следующему** запросу, не запрещает отправку текущего intent. Доказанно неотправленный запрос получает `notSent` через локальный `ConsumeNotSent` dispatch-контракт: внутренний guard адаптера тоже разрешает следующую плановую попытку; отправленный RPC не отменяется ручной командой.
- После подтверждённого результата журнал сохраняется до post-success read. Успех группы сохраняется после restart, исчезновения выбранного ID и отключения расписания.
- После crash до/после RPC engine видит тот же durable intent и не отправляет повтор с новым или прежним ключом. Неизвестный исход блокирует consume всей установки согласно консервативному контракту 13. Refresh/reconnect/таймаут не доказывают неприменение; пропажа ID/`noCredit`/непроверенный `redeemed` не доказывают успех.
- Без доказанного server key scope/TTL или selected-ID результата снятие неизвестности/сетевой replay не предоставлены. Реальные свойства и восстановление по доказательствам — 21. Ручной retry эту неизвестность не снимает.
- При неизвестном expiry можно сохранить выбранный час, но непроверенные сведения не разрешают consume: `AccountAdapter` 13 требует подтверждённую eligibility. Час всё равно заканчивается по сохранённому началу.

## CLI

Node 26.10.0. Команды/ответы — JSONL. Пример без сети/credentials, с новой временной установкой:

```sh
node src/cli.mjs --mode mock --state /tmp/auto-reset-demo.json <<'JSONL'
{"command":"init","language":"ru"}
{"command":"control","action":"select","commandId":"demo-select","expectedVersion":0,"creditId":"selected-013","automation":false}
{"command":"status","format":"markdown"}
JSONL
```

`init` повторно существующий файл не заменяет. Получайте `version` из свежего status перед следующей ручной командой; refresh/run тоже могут изменить версию. Пример `apply-now` после приведённого `select` при версии 1:

```json
{"command":"control","action":"apply-now","commandId":"demo-now","expectedVersion":1,"creditId":"selected-013","automation":false}
```

Поддерживаемые control actions:

| Действие | Поля и смысл |
| --- | --- |
| `select` | `creditId` (либо самый ранний допустимый ID); `deltaSeconds` для конечного срока или `scheduledAt`; `automation:false` для отсутствия автоматизации. Δ по умолчанию 3600. |
| `apply-now` | `creditId`; заменяет прежнее расписание одним ручным циклом с началом сейчас, без недельного условия; без предварительного `select` создаёт цикл из последнего сохранённого списка. Требует включённой установки. Явная замена часового цикла задаёт новый выбранный час; metadata/reconnect так не действуют. Завершённый неуспешный час повторяется через `retry`. |
| `retry` | `creditId`; только после завершения часового цикла без неизвестного consume/успеха. Новый час ограничен уже известным более ранним expiry. |
| `disable` / `resume` | `creditId` для выбранного цикла либо без ID для установки. Resume сохраняет исходные границы; не создаёт отсутствующее расписание. |
| `reconnect` | Сохраняет запрос переподключения. Выполняется отдельной командой CLI `reconnect`; не подтверждает consume и не продлевает час. Реальный вход/session lifecycle — 23/18; storage — 15. |
| `revoke` | Durable отключение установки и новых команд. Уже отправленный результат всё равно записывается. Внешний отзыв grants/Secrets — 15/18. |
| `weekly-auto` | `enabled` boolean. Общее правило: применить сброс с ближайшим сроком при подтверждённом исчерпании недельной квоты до её resetsAt; при 99% — окно наблюдения. Выключенная опция запрещает consume недельных и явно выбранных циклов и снимает наблюдение; расписание включается отдельно (`enable`). |
| `before-expiry` | `enabled` boolean. Общее правило «за 30 минут до истечения» для всех допустимых сбросов, без недельного условия. Выключенное правило снимает окна своих циклов. |

Все control actions требуют `commandId` и `expectedVersion`. Повтор того же ID/полей возвращает `duplicate:true` без нового действия, даже после restart/revoke. Другие поля под тем же ID → `command_id_reused`; устаревшая версия → `version_conflict`. Принятие команды (`accepted`) не является применением; `run` отдельно выполняет одну допустимую попытку. Durable очередь и queued/dispatch reconciliation — 17.

Открытый JSON control принимает только этот локальный CLI. Private workflow с 11 октября 2026 года (тикет 34) отклоняет его из `workflow_dispatch` как `open_command_rejected` без изменения state и consume. Там те же actions и поля передаются только внутри зашифрованной admin-команды `action:"control"`, а ID и версия берутся из её заголовка. Journal, fingerprint, duplicate и resume не меняются; ранее принятые ID сохраняются. Подробности — [private workflow](private-workflow.md#сериализация-и-команды).

Другие команды: `status` (`format:json|markdown`), `refresh`, `run` (необязательный `creditId`) и `reconnect`. Режим с `--state` не принимает raw `consume`. Старый CLI без state сохраняется как низкоуровневый synthetic стенд 13.

Отчёт показывает ID/expiry, выбранный момент/границу, задержку, последнюю попытку/результат, next attempt или отсутствие активного повторения, проблему metadata, возможность retry, принятые command ID и исход группы. Подтверждённый успех и неизвестный исход не подменяются принятием команды.
